2026-10-13T00:00Z  TASK-003  Implement registration and login authentication
Branch: ralph/task-003-auth (api repo) | root repo: master
Commit: api@028d4e1d98760f3796609299435370d65db0144b
=====================================================================

Summary:
- Added an auth module (api/src/auth) with register, login, refresh, logout, and me
  endpoints under /api/v1/auth.
- Passwords hashed with bcrypt cost 12; responses return {user, accessToken} and never the
  passwordHash. Access token is a short-lived (15m) JWT; refresh token is a 7d JWT delivered
  in an httpOnly cookie scoped to path /api/v1/auth.
- Invalid credentials return 401 with one message ("Invalid email or password") for both a
  wrong password and an unknown email; duplicate registration returns 409.
- Added DTO validation (class-validator/class-transformer) with a global ValidationPipe
  (whitelist + forbidNonWhitelisted + transform) and cookie-parser in the bootstrap.
- GET /auth/me is implemented by verifying the Bearer token and loading the user; the
  reusable guard + @CurrentUser() decorator are intentionally left for TASK-004.

Important files:
- api/src/auth/auth.module.ts, auth.service.ts, auth.controller.ts, auth.constants.ts
- api/src/auth/dto/register.dto.ts, api/src/auth/dto/login.dto.ts
- api/src/auth/auth.service.spec.ts, api/test/auth.e2e-spec.ts
- api/src/main.ts (cookieParser + ValidationPipe), api/src/app.module.ts (AuthModule)
- api/tsconfig.build.json (tsBuildInfoFile fix), api/README.md (auth docs + env vars)

Validation (run in api/; machine exports NODE_ENV=production):

- npm run lint         -> PASS
- npm run typecheck    -> PASS
- npm run build        -> PASS (dist/main.js present; verified complete across 3 repeat builds)
- npm test             -> PASS (7 tests: 1 health + 6 auth service)

Acceptance criteria:
- Registration stores a bcrypt hash and never returns it -> met (e2e + unit + DB check).
- Valid login returns access token + refresh cookie -> met (e2e + curl).
- Invalid credentials 401 without field disclosure -> met (identical message asserted).
- /auth/refresh issues a new access token from a valid cookie -> met (e2e + curl).
- /auth/me returns the profile -> met (e2e + curl).
- Authentication e2e tests pass -> met (test/auth.e2e-spec.ts, 10 tests).

Remaining concerns:
- @nestjs/jwt is pinned to ^11: v12.0.3 is ESM-only ("type":"module") and its dist/index.js
  breaks this CommonJS/Jest build ("Cannot use import statement outside a module"). v11 is CJS
  and matches the Nest 11 stack; keep it pinned until the project moves to ESM.
- Fixed a pre-existing build bug: with deleteOutDir:true + incremental:true, a second
  `npm run build` wiped dist but emitted nothing (tsbuildinfo claimed outputs were up to date),
  leaving a dist without main.js. tsconfig.build.json now writes the build info into
  ./dist/tsconfig.build.tsbuildinfo so deleteOutDir clears it and every build is complete.
- The refresh cookie Secure flag is controlled by an explicit COOKIE_SECURE env (default false)
  rather than NODE_ENV, so e2e stays deterministic under the ambient NODE_ENV=production.
  Production/compose hardening (COOKIE_SECURE=true, JWT_REFRESH_SECRET) belongs with TASK-007/
  TASK-014.
- Refresh tokens are not stored server-side and are not rotated on refresh, and logout only
  clears the cookie (a stolen refresh token stays valid until it expires). Acceptable for this
  task's scope; revisit if the PRD later requires revocation.
- GET /auth/me verifies the token inline; TASK-004 will extract the reusable guard + decorator.
- Component README documents the endpoints; the root README/auth section is finalized in
  TASK-007/TASK-014.
